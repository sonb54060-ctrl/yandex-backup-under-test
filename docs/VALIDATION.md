Тесты покрывают условную запись состояния и конфликт владельцев, повторные вызовы, потерю ответа создания без повторного создания, отклонение по квоте, незавершенную резервную копию, ошибку операции, просроченное восстановление, задержанную видимость ресурса, запрет удаления чужого/исходного кластера, отказ в правах удаления и независимую уборку.

Проверки вложений покрывают версию, SHA-256, права, размер, область допустимых ключей и время проверки. Проверки БД покрывают адаптер чтения с read-only транзакцией и ограничением числа строк. HTML экранирует значения отчета.

S3 эмулирует Moto. Облачный API подменен тестовым адаптером, реальная БД в локальной демонстрации не запускается. Эти результаты не подтверждают работоспособность облачной интеграции.

Схема YaWL загружена из [официального репозитория](https://github.com/yandex-cloud/json-schema-store/blob/master/serverless/workflows/yawl.json). SHA-256 использованного файла: `dfa59c3ee0535d0bdbc3083cbedf65a6cb9875f3c5afc77ada1664b3854fbd6e`.

Установка расписания проверена в облаке. У поля `schedule` семантика Optional+Computed, поэтому для выключения в инструкции предусмотрен явный `yc serverless workflow update <id> --remove-schedule` перед применением `enable_daily_schedule = false`. API подтвердил отсутствие расписания. Попытка пересоздания выявила дополнительное ограничение: Workflows с расписанием нельзя удалить. Фактический запуск в назначенное время не проверялся.

Обе новые страницы собраны в HTML через `yfm content --strict` (Diplodoc 5.61.1) на checkout `5228495525074412a96e60fc6e5773c495f0c634`; проверены шесть новых ссылок навигации и YAML оглавлений. Полная сборка всего репозитория не выполнялась.

Положительный опыт объединяет перезапись и маркер удаления в одном восстановлении. Отдельные облачные восстановления только для перезаписи или только для маркера не выполнялись; эти случаи также покрыты локальной демонстрацией.

## Что не подтверждено отдельным облачным опытом

- Принудительное прерывание Workflows во время создания кластера и последующая уборка по TTL.
- Потеря ответа создания, задержанная видимость ресурса, реальные отказы IAM во время удаления и восстановление после них.
- Запуск именно по наступлению ежедневного расписания. Установка и снятие проверены через API, календарного запуска не ожидали.
- Полный аудит всех облачных журналов на отсутствие секретов. Проверены формат выбранных записей и приватность объектов, а не все возможные пути ошибок.
- Потеря бакета, региона, большие объемы, рабочая нагрузка и обещания production RTO/RPO.


Тесты обработки сбоев используют подмененный облачный API. Они не заменяют испытание перечисленных отказов на реальных ресурсах. Категорию `new-solution` и размер гранта определяют редакторы программы.
