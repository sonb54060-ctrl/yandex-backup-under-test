# Бэкап под проверкой

Учебный стенд для проверки согласованного восстановления Managed Service for PostgreSQL и вложений в Yandex Object Storage. База восстанавливается в новый приватный кластер; каждая ссылка на файл проверяется по `version_id` и SHA-256. После проверки временный кластер удаляется.

**Статус:** реализация проверена в Yandex Cloud. Положительный опыт — PASS; отрицательный — ожидаемый FAIL / MISSING_VERSION. Оба временных кластера автоматически удалены. Локально проходят 32 теста. Платные ресурсы и сети стенда удалены; тестовые каталоги поставлены на удаление. Подробнее — [журнал облачного прогона](docs/CLOUD-RUN.md). Это учебный пример, еще не опубликованное руководство Яндекса.

## Быстрый локальный запуск

Python 3.12 или новее:

```sh
python -m venv .venv
```

Активируйте окружение: Windows PowerShell — `./.venv/Scripts/Activate.ps1`; Linux/macOS — `source .venv/bin/activate`.

```sh
python -m pip install -r requirements.txt
python -m pip install -e ".[dev]"
python -m pytest -q
python -m backup_lab.cli demo
```

Демонстрация не обращается к облаку. Она использует S3-эмулятор Moto и контрольный набор записей в памяти; реальный PostgreSQL здесь не запускается. Результат: `intact`, `overwritten`, `delete-marker` → PASS; `missing-version` → FAIL. HTML и JSON сохраняются в `artifacts/local-demo/`.

## Облачный сценарий

Полное прохождение — в [практическом руководстве](docs/yandex-cloud/ru/_tutorials/archive/backup-under-test.md).

1. `infra/base` создает исходный учебный PostgreSQL, две раздельные сети, бакеты, аккаунты и секреты.
2. `scripts/export_outputs.py` экспортирует несекретные параметры; `scripts/package.py` собирает архив функций с CA-сертификатом Яндекса.
3. `infra/automation` создает функции, Workflows и независимый таймер уборки. Ежедневные учения по умолчанию выключены.
4. Оператор создает синтетические данные, ручную резервную копию и контрольную точку.
5. Workflows выполняет восстановление, проверки и удаление. Запускать каждый опыт нужно с новым `run_id`.

## Что проверяется

- Число заказов, уникальность идентификаторов, сумма и хеш всего набора записей.
- Чтение конкретной версии каждого файла и SHA-256 его содержимого.
- Отдельная диагностика отсутствующей версии и отсутствующих прав.
- Время восстановления вместе с проверкой относительно заданной цели.
- Подтвержденное отсутствие временного кластера после удаления.

## Защита от сбоев

Контроллер использует `If-None-Match` и `If-Match` в S3 для сериализации запусков. Намерение восстановить кластер сохраняется до запроса API. Если ответ потерян, запрос создания не повторяется: ресурс ищется по служебным меткам и удаляется. Если исход операции неизвестен, состояние `MANUAL_REVIEW` блокирует новые запуски. Независимый таймер каждые 15 минут ищет просроченные ресурсы только своего стенда.

Временный кластер создается через API, а не Terraform: у ресурса один владелец. Исходная база защищена от удаления. Бакеты закрыты; тестовая функция записи отделена от контроллера и недоступна аккаунту Workflows.

## Границы

- Один исходный кластер, один активный запуск, максимум 100 заказов и 1 МиБ на вложение.
- Исходная БД не должна изменяться между подготовкой учебного набора и завершением ручной копии. Контрольная точка фиксирована: расписание проверяет ее, а не автоматически выбирает свежайший бэкап.
- Восстанавливается БД; сохраненные версии файлов читаются из исходного бакета. Потеря бакета или региона этим стендом не покрывается.
- SHA-256 набора строится по фиксированной схеме учебных заказов. Для другого приложения нужны собственные проверки.
- Это не общий атомарный снимок PostgreSQL и S3. Приложение должно записывать `version_id` и сохранять старые версии весь срок действия резервной копии.
- Возраст контрольных данных не называется RPO; время лабораторного опыта не гарантирует RTO рабочего приложения.
- Статические S3-ключи создаются непосредственно в Lockbox. Пароль учебной БД присутствует в Terraform state: храните state как секрет, вне Git и общих папок.

## Проверка проекта

```sh
python -m pytest -q
python -m ruff check --config pyproject.toml src tests scripts
python scripts/validate_workflow.py
terraform fmt -check -recursive infra
terraform -chdir=infra/base init -backend=false
terraform -chdir=infra/base validate
terraform -chdir=infra/automation init -backend=false
terraform -chdir=infra/automation validate
```

Последние команды проверяют конфигурацию по схеме настоящего провайдера, но не создают ресурсы и не подтверждают права IAM, сетевую связность или поведение API в облаке.
